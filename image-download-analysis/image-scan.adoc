= RHACS Scanner

RHACS Scanner is the integrated vulnerability scanning capabilities that analyze container images and cluster workloads for security risks. It primarily comprises two engines:

- **Scanner V4**: Introduced in RHACS v4.4, this engine uses ClairCore to provide accurate detection of OS packages, language dependencies (like Go, Python, Java), and Go binaries.
- **StackRox Scanner**: The legacy default scanner, originally a fork of Clair v2, which remains essential for RHCOS node scanning and platform vulnerabilities (e.g., OpenShift, Kubernetes) where Scanner V4 support is still being expanded.

The scanners pull images from registries, analyze layers to identify installed packages, and match them against known Common Vulnerabilities and Exposures (CVE) databases to generate risk-prioritized reports in the RHACS portal.

== RHACS Image Scanning (Scanner V4)
=== New Image

. Sensor detects the deployment, and Central requests the Scanner Indexer to download and index the image.
. The Indexer pulls image metadata from the registry, determines the layers, and downloads each previously un-indexed layer.
. The Indexer produces an `IndexReport` (list of packages, OS, language dependencies) and stores it in the `scanner-v4-db`.
. Central then requests the Matcher to match the image to known vulnerabilities.
. The Matcher fetches the latest vulnerability data from Central, retrieves the `IndexReport`, and produces the final vulnerability report.

=== Existing (already-indexed) Image

. Sensor detects the deployment and Central calls the Scanner Indexer.
. The Indexer fetches the image manifest from the registry to read its layer SHA digests. It checks `scanner-v4-db` and finds that index data already exists for these layer digests.
. The Indexer bypasses downloading and re-analyzing the layer blobs from the registry, saving network bandwidth and CPU resources.
. The scanner reuses the existing `IndexReport` from `scanner-v4-db`, matches it against the current CVE feeds, and delivers the report to Central DB.

=== Periodic Image Reprocessing Loop

- Every 4 hours (configurable with `ROX_REPROCESSING_INTERVAL` environment variable), Central runs an automated image reprocessing loop for all active (deployed) images.
- The Matcher evaluates the existing `IndexReport` against vulnerability definitions that Central updates every 5 minutes (configurable with `ROX_SCANNER_VULN_UPDATE_INTERVAL` environment variable).
- If new CVEs are published that affect packages in the stored index, Central DB is updated and policy violations are created or resolved automatically.

[NOTE]
====
- The `ROX_SCANNER_VULN_UPDATE_INTERVAL` environment variable applies to the connection between Central and the `definitions.stackrox.io` feed. Both the StackRox Scanner and Scanner V4 use vulnerability data from Central that is obtained from this feed.
- This `definitions.stackrox.io` feed combines vulnerability definitions from upstream sources, and it refreshes every 3 hours.
====

== Pruning and Garbage Collection
=== Workload Removal and Central Database Retention Pruning

* RHACS does not automatically remove scan data from active (deployed) images; it periodically re-scans them every 4 hours to update vulnerability definitions.
* When the workload deployment is removed from the cluster, RHACS marks the image as inactive.
* Inactive images are immediately removed from the periodic reprocessing loop to conserve cluster resources.
* Scan data for the inactive image remains in Central DB for 7 days (configuration in **Platform Configuration → System Configuration → Images no longer deployed**).
* Once the retention period expires, Central's background pruner permanently deletes the image's scan data from Central DB.

Deleting or pruning inactive image scan data from **Central DB** (`central-db`) has several direct operational and historical consequences:

* Storage and performance benefits:
  ** Reduced storage space usage, lowering the risk of running out of space on the Central DB Persistent Volume Claim (PVC).
  ** Reduced memory and CPU overhead on both the `central` and `central-db` pods, mitigating the risk of Out-of-Memory pod restarts.
  ** Faster portal and API performance, as there is less data to load, resulting in improved response times.
* Loss of historical audit and reporting data:
  ** Permanent removal of past scan data (scan findings, package inventories, and vulnerability findings).
  ** Inability to audit past image states or generate compliance and vulnerability reports for images whose scan data has been deleted.
* No impact on active security or network bandwidth:
  ** Running deployments continue to be monitored and enforced normally.
  ** Inactive images are excluded from Central's 4-hour periodic vulnerability reprocessing loop anyway.
* Automatic re-scanning upon redeployment:
  ** RHACS automatically detects the image and performs a fresh scan against the latest vulnerability definitions.

[NOTE]
====
* Setting the data retention period to **0** disables pruning and retains inactive image data indefinitely.
* It is **not** recommended to disable pruning of inactive image data.
====

=== Scanner V4 Layer Index Garbage Collection

Independent of Central, Scanner V4 uses two distinct background garbage collection (GC) processes to manage storage and maintain performance:

* **Throttled GC**: every 4 hours, purges up to 100 expired manifests (7-30 days after indexing) from `scanner-v4-db`.
* **Full GC**: every 24 hours, performs a comprehensive cleanup of all expired manifests to reclaim significant space.

[NOTE]
====
- Purging a manifest from `scanner-v4-db` does **not** delete the active image scan data or vulnerability history from Central DB.
- If Central or a `roxctl` scan explicitly requests a fresh index for an active image after its layer index was purged, Scanner V4 transparently fetches the manifest and layer blobs from the registry to rebuild the `IndexReports` in `scanner-v4-db`.
====

The following environment variables control Scanner V4 garbage collection (see https://github.com/stackrox/stackrox/blob/master/pkg/env/scannerv4.go):

[cols="3,1,3", options="header"]
|===
| Environment Variable
| Default
| Description

| ROX_SCANNER_V4_MANIFEST_DELETE_INTERVAL_START
| 7 days
| Minimum age before a manifest becomes eligible for deletion in throttled GC run.

| ROX_SCANNER_V4_MANIFEST_DELETE_DURATION
| 23 days
| Manifest aged between `ROX_SCANNER_V4_MANIFEST_DELETE_INTERVAL_START` and (`ROX_SCANNER_V4_MANIFEST_DELETE_INTERVAL_START` + `ROX_SCANNER_V4_MANIFEST_DELETE_DURATION`) days are considered for random deletion during throttled GC runs.

| ROX_SCANNER_V4_MANIFEST_GC_INTERVAL
| 4 hours
| The interval between throttled GC runs.

| ROX_SCANNER_V4_MANIFEST_GC_THROTTLE
| 100
| The number of manifests to garbage collect during a typical throttled GC run.

| ROX_SCANNER_V4_FULL_MANIFEST_GC_INTERVAL
| 24 hours
| The interval between full GC runs.
|===

Extending the Scanner V4 garbage collection retention settings (e.g., increasing the manifest retention period from 7-30 days to 14-60 days) has several consequences:

* Increased disk space usage in `scanner-v4-db`:
  ** Storage expansion: Retaining `IndexReports` for longer periods increases the amount of historical data stored over time.
  ** PVC capacity risk: The accumulation of `IndexReports` can exhaust available PVC capacity. Running out of storage can lead to database errors or degraded scanning performance.
* **Reduced network traffic and registry load through extended caching**:
  ** Reduced Blob Downloads: Scanner V4 can avoid re-downloading and re-analyzing image layer blobs when the corresponding cached data remains available and valid.
  ** Bandwidth and CPU savings: Extended caching can reduce network traffic between the Scanner V4 Indexer and container image registries, as well as CPU and I/O overhead on scanner pods and registry endpoints.
* No expected negative impact on new vulnerability (CVE) reporting.

== Central DB vs Scanner V4 DB

Here is a side-by-side comparison of the usage, role, and operational characteristics of **Central DB** (`central-db`) and **Scanner V4 DB** (`scanner-v4-db`):

[cols="1,2,2", options="header"]
|===
| Feature
| Central DB (`central-db`)
| Scanner V4 DB (`scanner-v4-db`)

| **Primary Role**
| Main persistent datastore for the RHACS platform control plane.
| Specialized datastore for image layer analysis and vulnerability matching.

| **Data Stored**
| System configurations, security policies, policy violations, cluster events, RBAC mappings, compliance results, and final vulnerability scan reports.
| Raw vulnerability feeds/bundles (Red Hat VEX, OSV, NVD) and layer-by-layer package inventory reports (`IndexReports`).

| **Deployment Location**
| Installed exclusively on the cluster hosting Central Services.
| Installed on the Central cluster (alongside Matcher and Indexer) and optionally on Secured Clusters for local/delegated scanning.

| **Data Retention and Purging**
| Configured via **Platform Configuration → System Configuration → Images no longer deployed**.
| Managed automatically by Scanner V4 Indexer background garbage collection, configurable with environment variables.

| **Impact of Storage Loss / Pod Restarts**
| Critical. Loss causes loss of platform settings and historical violations unless restored from a backup.
| Non-critical. Active scan reports in Central DB remain intact. Scanner V4 simply re-fetches layers from the registry to rebuild the `IndexReport` if needed.
|===

== Container Registry Authentication (Image Pull Secrets)

RHACS automatically discovers image pull secrets (`dockercfg` and `dockerconfigjson`) across monitored namespaces. It uses these secrets to build autogenerated image integrations, typically with the `Autogenerated` prefix.

Disable autogenerated image integrations by setting the `ROX_DISABLE_AUTOGENERATED_REGISTRIES` environment variable to `true`.

When auto-discovery is disabled, RHACS authenticates with container registries using three primary methods:

* **Manually configured image integrations**: Manual integrations always take precedence over autogenerated ones for matching registry endpoints.
* **Delegated image scanning**: If delegated image scanning is enabled, image scanning is performed directly by the scanner deployed on SecuredClusters. Authentication occurs in the following order:
. Synchronized manual image integrations from Central
. The pull secret in the workload namespace
. The OpenShift global pull secret
. Anonymous or unauthenticated access
* **Built-in default integrations**: Preconfigured default integrations supplied with RHACS.

== Configure Environment Variables for RHACS Components

The following example uses `.spec.overlays` field to apply JSONPath-based patches to Central and Scanner V4 Indexer:

[source,yaml]
----
apiVersion: platform.stackrox.io/v1alpha1
kind: Central
metadata:
  name: stackrox-central-services
  namespace: stackrox
spec:
  central:
    exposure:
      route:
        enabled: true
  scannerV4:
    scannerComponent: Enabled
  overlays:
    - apiVersion: apps/v1
      kind: Deployment
      name: central
      patches:
        - path: 'spec.template.spec.containers[name:central].env[-1]'
          value: |
            name: ROX_REPROCESSING_INTERVAL
            value: "2"
    - apiVersion: apps/v1
      kind: Deployment
      name: scanner-v4-indexer
      patches:  # change triggered gc interval to 2 hours, and delete manifests aged between 14-30 days
        - path: 'spec.template.spec.containers[name:indexer].env[-1]'
          value: |
            name: ROX_SCANNER_V4_MANIFEST_DELETE_INTERVAL_START
            value: "14d"
        - path: 'spec.template.spec.containers[name:indexer].env[-1]'
          value: |
            name: ROX_SCANNER_V4_MANIFEST_DELETE_DURATION
            value: "14d"
        - path: 'spec.template.spec.containers[name:indexer].env[-1]'
          value: |
            name: ROX_SCANNER_V4_MANIFEST_GC_INTERVAL
            value: "2h"
----
